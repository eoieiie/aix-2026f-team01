# AI 공통 컨텍스트 / Shared Agent Context

> **쓰는 법** — AI 도구(Claude · ChatGPT · Gemini · Copilot 등 무엇이든)에게 이 프로젝트 작업을
> 시킬 때, **새 대화의 맨 처음에 이 문서를 읽게 한다.** 저장소를 열 수 있는 도구는 "team/AGENTS.md 를 읽고
> 따르라"고 하면 되고, 못 여는 도구는 전체를 붙여넣는다. 그다음 작업을 지시한다.
> 도구가 달라도 같은 문서를 주면 결과가 크게 벌어지지 않는다.
>
> 이 문서는 **저장소 안에서 버전 관리된다.** 규약이 바뀌면 여기를 고치고 커밋한다.
> 각자 따로 저장해두고 쓰면 사람마다 다른 규약을 주게 되므로, **항상 최신 `main`에서 복사해 쓴다.**

## 0. 너에게 주는 지시

너는 이 팀의 프로젝트를 돕는다. 아래 규약을 **모든 답변과 산출물에 적용**한다.
규약과 내 요청이 충돌하면 **먼저 그 충돌을 알려주고 멈춘다.** 임의로 어느 한쪽을 고르지 않는다.

### 반드시 지킬 것

1. **모르면 지어내지 마라.** 이 문서와 내가 준 코드에 없는 함수·컬럼·API·파일 경로를
   추측해서 쓰지 마라. 필요하면 **"그 정보가 없다. 무엇을 주면 되는가"**라고 되물어라.
2. **완료 조건이 없으면 코드를 쓰지 마라.** 무엇이 되면 성공인지 먼저 물어보고,
   합의된 뒤에 작성한다.
3. **설명은 한국어로.** 코드·변수 이름·브랜치 이름은 영어.
4. **한 번에 한 가지만 바꿔라.** 요청하지 않은 리팩터링·파일 정리·의존성 추가를 끼워 넣지 마라.
5. **답변 끝에 `판단 기록` 세 줄**을 붙여라. 아래 7번 형식.

### 절대 하지 말 것

- **실제 개인정보**(이름·학번·연락처·이메일 명단 등)를 다루거나 예시로 만들어내지 마라.
  테스트 데이터가 필요하면 **가짜 데이터를 생성**하거나 **구조만 남기고 값을 비운다.**
- **다른 팀의 코드·이전 학기 과제 코드**를 가져오지 마라.
- API 키·비밀번호·토큰을 코드에 직접 쓰지 마라. 환경변수로 분리한다.
- 이해 없이 넘어가도 되는 코드를 만들지 마라. **우리는 발표에서 동작 원리를 질문받는다.**

## 3. 규약 — 어떻게 쓰는가

- 협업 절차·브랜치·커밋 규칙은 [`team/WORKFLOW.md`](WORKFLOW.md)를 따른다. **요약:**

## 6. 작업을 시킬 때 이 네 칸을 채워 준다

이 문서를 붙여넣은 뒤, 실제 지시는 아래 형식으로 준다.

```
[지시]
무엇을 해달라는지 한 줄.

[근거]
관련 파일의 실제 코드 전문. 요약하지 않는다.

[규약]
이 작업에만 해당하는 추가 규칙이 있으면.

[완료 조건]
```

**`[완료 조건]`이 비어 있으면 코드를 쓰지 말고 먼저 물어라.**

```

- 이유:
- 확인 방법:
```

이 세 줄이 흐름이 끝났을 때 `PROMPTS.md` 표 한 줄의 재료가 된다 (8절).

## 8. 기록 — 흐름이 끝날 때마다 바로 올린다

**언제:** 한 흐름이 끝나 결정, 폐기, 배운 것이 하나 생겼을 때. 사람이 "기록해"라고 하면 바로, 말하지 않아도
그런 흐름이 끝났다고 판단되면 "PROMPTS.md에 기록할까?"라고 먼저 묻는다. 질문 하나하나는 적지 않는다.

**무엇을:**
1. `PROMPTS.md` 표 맨 아래에 한 줄. `| 날짜 | 이름 | 내용 | 명령 (원문) | 판단 | 결과·이유 | 검증 |`
   - 이름은 `git config user.name`이 아니라 GitHub 아이디. 모르면 묻는다
   - 명령은 사람이 한 말 원문. 길면 핵심 문장만 따옴표로 옮기고 "(일부)". 지어내거나 다듬지 않는다
   - 셀 안의 줄바꿈은 `<br>`, `|`는 `\|`
2. 팀 전체에 걸리는 결정(중요도 상·중)이면 `docs/decisions.md` 맨 아래에도 한 줄. 하지 않기로 한 것은
   "<무엇> 하지 않음", 반대 의견은 이유 칸에 "반대: <누가 무엇을>"
3. 두 파일 모두 **줄 추가만** 한다. 예전 줄을 지우거나 고치지 않는다.

**올리는 법:**
- 지금 작업 브랜치가 있으면 그 브랜치에 커밋해 같은 PR에 들어가게 한다.
- 작업 브랜치가 없으면 `docs/log-YYYYMMDD-<GitHub아이디>` 브랜치를 만들어 커밋하고 PR을 연다.
  리뷰어는 `team/WORKFLOW.md` 4장 순번의 다음 사람.
- 커밋 전에 `git pull --rebase origin main`. 커밋 메시지는 `docs: <내용> 기록`.
- 커밋에 AI 공동저자 줄을 넣지 않는다. 커밋은 그 사람 계정으로 찍힌다.

**충돌이 나면:** 두 파일은 `.gitattributes`에서 `merge=union`이라 로컬에서 합칠 때 양쪽 줄이 모두 남는다.
그래도 충돌 표시가 남으면 **양쪽 줄을 모두 살리고** 날짜순으로 놓는다. 어느 줄도 지우지 않는다.
GitHub PR이 충돌로 표시되면 자기 브랜치에서 `git pull --rebase origin main` 후 `git push --force-with-lease`.
`main`에는 강제 push하지 않는다.

## 9. 명세를 바꿀 때

- `docs/spec.md`는 팀 회의에서 정한다. 사람이 회의 날짜나 이슈 번호를 주지 않으면 명세를 고치지 않는다.
  바꿔야 할 것 같으면 이유를 말하고 멈춘다.
- 회의에서 바뀐 내용을 반영할 때는 `docs/decisions.md`에 한 줄 더하고, 근거 칸에 `회의 YYYY-MM-DD`.
- 구현 중에 완료 조건과 다르게 만들지 않는다. 다르게 해야 하면 먼저 사람에게 묻는다.

- 작업을 시작할 때 그 절의 완료 조건을 사람에게 먼저 다시 설명하고, 확인받은 뒤 코드를 쓴다.

## 왜 이 문서가 있는가

2주차에 배운 것 — 에이전트는 **관찰·판단·행동의 반복 루프**로 돌고, 환각은 모델의 결함이 아니라
**근거 부족 상태의 산물**이다. 컨텍스트에 실제 코드와 규약이 있으면 그 위험이 줄어든다.

같은 과제를 지시 한 줄만 주고 시켰을 때와, 규약·실제 코드·완료 조건을 함께 주고 시켰을 때
결과가 갈렸다. 지어낸 이름 3개 대 0개, 규약 위반 5개 대 0개였다.
**결과를 가른 것은 모델이 아니라 입력이었다.**

네 사람이 서로 다른 도구를 쓰더라도 **같은 문서를 주면 같은 방향의 산출물이 나온다.**
그래서 이 문서는 각자의 메모가 아니라 저장소 안의 파일이어야 한다.
