## 1. 학교 앞 가게 전처리

1. 공공데이터에서 `영업/정상`만 남기고 좌표가 없는 곳은 뺀다. Bessel 1841 중부원점 TM(EPSG:5174)을 역투영하고, 7변수 변환으로 WGS84 위경도로 바꾼다. 정문 `(37.2998, 126.8369)`에서 하버사인 직선거리 1,200m 이내만 남긴다.
2. 업태 `기타`, `정종/대포집/소주방`과 이름에 `닭`이 없는 `호프/통닭`을 뺀다. 같은 이름이나 지점 표기를 비교해 오픈스트리트맵과 겹치면 오픈스트리트맵을 남긴다. 업태로 종류를 나누고(서버가 사람 확인으로 고친 8곳은 `KIND_FIXES`), 대표 메뉴는 둘로 나눠 낸다. `menus`는 가게 이름에 든 음식 이름과 별칭 낱말(`MENU_ALIASES`)로 근거가 있는 것만, `menus_guess`는 업태나 오픈스트리트맵 태그로 흔한 메뉴(중국식 짜장면 짬뽕 탕수육 등)를 **짐작**한 것이다. 짐작의 음식 종류가 가게 종류와 다르면 버린다. 앱은 짐작을 가게 상세나 그림에 보이지 않고 찾기와 순서에만 쓴다(서버 0051). 실제 판매 메뉴나 도보 경로를 확인한 값은 아니다.
3. 카페는 일반음식점에서 업태와 이름으로, 휴게음식점·제과점에서는 방문 후보의 관리번호로, 오픈스트리트맵에서는 카페·아이스크림·빵집 추출본으로 고른다. 코지홀리데이는 공공데이터 좌표가 없어 [PR #96의 자료 설명](https://github.com/eoieiie/aix-2026f-team01/pull/96/files)에 적힌 오픈스트리트맵 건물 좌표를 사용한다. 방문 후보 표시는 현재 제휴 상태를 뜻하지 않는다.
4. `out/restaurants.csv`, `out/cafes.csv`를 생성하고, 2026-11-25 서버 추출본과 `source_id`로 대조한다. 이 스크립트는 앱이나 서버 데이터를 수정하지 않는다.

## 2. AI 재료 태그 평가 (2026-11-25)

**정답은 사람이 아니라 서로 다른 AI 두 개와 판정자 하나의 합의다.** 그래서 "기준 정답"이라 부르고 사람 정답이라 하지 않는다. 사람 정답은 앱의 사람 확인 기능(`ai_feedback`, "맞아요"와 "재료 더하기")으로 쌓는 중이다. 실제 원재료 보증이나 알레르기 안전 판단에는 쓸 수 없다.

1. 메뉴 80개: 직접 적은 메뉴 40개(서버에 실제로 들어온 가게 이름과 메뉴 10개, 외국 음식 13개, 숨은 재료 한식 11개, 식단 판단 6개)와 기본 메뉴 40개.
2. 평가자 A(Claude, `annot_a_claude.csv`)와 평가자 B(GPT, `annot_b_gpt.csv`)가 앱 답을 보지 않고 태그 9개마다 0(거의 없음), 1(가게나 버전에 따라), 2(대부분 가게의 기본 레시피)와 근거 한 줄을 따로 매겼다.
3. 일치도: 둘 다 매긴 칸으로 세 단계 일치율, 가중 카파(선형, 제곱), 있다/없다(1 이상)로 묶은 카파를 낸다.
4. 판정자(세 번째 AI)가 시스템 답을 보기 전에 갈린 144칸을 두 근거를 읽고 정했다(`consensus.csv`의 판정 이유). 평가자 B가 판단 불가로 비운 가게 이름 5개는 대표 메뉴로 추정했고, 떼드떼는 정답 없이 메뉴 아님만 본다.
5. 시스템 평가: 칸마다 정답(0/1/2)과 시스템 표시(확실, 약함, 없음)를 맞춘다. **놓침** = 정답 2인데 아무 표시 없음(안전 실패), **과잉 확실** = 정답 0인데 "못 먹는 사람이 있어요"(괜찮은데 안 괜찮아짐), **약한 표시 과잉** = 정답 0인데 "들어갈 수 있어요".
   - (가) 낱말 표만: 서버 `foods.tags`(직접 적은 메뉴는 낱말 표와 기본 메뉴 이름 부분 일치)
   - (나) 예전 AI 판 1: 11/25 오전 서버의 `ai_tags`(그때는 모두 확실로 쓰였다), 답 실패 4개는 표시 없음
   - (다) 예전 합침: 판 1 낱말 표와 AI의 합집합(모두 확실)
   - (라) 지금 판 2 두 단계: 11/25 운영 서버에 시험 모임(동네 `zz_test`)을 만들어 40개를 직접 적기로 다시 올려 받은 답. 낱말 표는 확실, AI 태그는 약함
6. 기본 메뉴 40개는 고치기 전(`base_tags_before.csv`)과 0045로 고친 뒤(`base_tags_after.csv`)의 확실과 약함을 같은 정답으로 잰다.

## 3. 사람 정답표 (2026-11-26, 채우는 중)

2절의 기준 정답은 AI 합의라 발표에서 성능 숫자로 쓰지 않는다(`docs/decisions.md` 2026-11-25). 같은 직접 적은 메뉴 40개(M01~M40)를 팀원 세 명이 따로 매겨 다시 잰다.

1. Aninnom은 `data/human_a_aninnom.csv`, Ruty041은 `data/human_b_ruty041.csv`, GONI1130은 `data/human_c_goni1130.csv`를 채운다(구글 시트로 매기고 CSV로 옮겨도 된다). 서로의 시트, AI 평가자 시트(`annot_*`), `consensus.csv`, 앱 화면의 AI 답은 보지 않고 매긴다. 서로 보지 않게 모두 다 채울 때까지 채운 시트를 커밋하지 않는다
2. 태그 9개마다 0(거의 없음), 1(가게나 버전에 따라), 2(대부분 가게의 기본 레시피). 2절과 같은 기준이다
3. 가게 이름(찌개찌개, 보배반점 등)이면 `메뉴 아님(1=아님)`에 1을 적는다. 대표 메뉴가 짐작되면 그 메뉴로 태그를 매기고, 모르면 태그를 비운다. `메모`는 자유롭게 적는다
4. 다 채우면 `python3 03_human_answer_key.py`가 두 사람씩 일치도를 내고, 칸마다 두 명 이상이 같은 값을 사람 정답으로 쓴다(다수결). 셋이 0, 1, 2로 다 갈린 칸처럼 다수결로 못 정하는 칸만 같이 정해 `data/human_decided.csv`(`id,태그,값,이유`)에 적는다. 세 번째 시트가 없으면 두 사람이 같은 칸만 쓴다. 두 사람만으로 해 보니 351칸 중 152칸이 갈려(세 단계 일치 59.3%, 가중 카파 0.444) 세 번째 사람을 넣었다
5. 다시 돌리면 사람 정답으로 (가) 낱말 표만, (나) AI 판 1, (다) 합침, (라) 판 2, (마) 판 3(`system_v3.csv`가 있을 때, 아래 절)의 놓친 재료 비율과 괜히 붙은 확실 경고 비율을 내고, AI 기준 정답이 사람 정답과 얼마나 맞는지도 낸다

덜 찼으면 채운 칸 수만 내고 멈춘다. 절반 이상이 비운 칸(대표 메뉴를 모르는 가게 등)은 정할 값이 없는 칸으로 둔다. 세 번째 시트가 덜 찼으면 그 빈칸은 표 없음으로 보고 진행한다. 계산 함수는 02의 것을 그대로 쓴다. 세 시트에 모두 AI 합의(`consensus.csv`)를 넣고 돌리면 2절 출력과 같은 숫자가 나오는 것을 확인했다(놓침 41/48, 4/48, 4/48, 2/48 등). 줄임말(제육, 부찌 등)은 이 40개에 없어서, 앱에 다시 올려 시스템 답을 받기 전에는 잴 수 없다.

| (라) 판 2 두 단계 | 6/52 (11.5%) | 0/127 (0.0%) | 10 |
| (마) 판 3 두 단계 | 3/52 (5.8%) | 0/127 (0.0%) | 11 |

(마)가 놓친 칸은 M06 쥬시 모찌 dairy(판 3이 메뉴 아님으로 봤다), M14 포케 egg, M29 잔치국수 egg다. 쥬시 모찌는 판 2 프롬프트로도 네 번 중 세 번 메뉴 아님이 나오는 흔들리는 칸이고, 잔치국수 달걀(지단)은 같은 판 3 프롬프트를 따로 네 번 물으면 네 번 다 붙었다. 모델 답이 물을 때마다 조금씩 달라서 한 번 뽑은 값이다. 가게 이름 입력 5개는 판 2와 같다(놓침 5/8, 괜히 붙은 확실 경고 0/14).

한계: (마)는 (라)가 놓친 칸을 보고 고친 뒤 같은 메뉴로 다시 잰 값이다(같은 자료로 고친 뒤 잰 값). 새 메뉴에서의 성능보다 좋게 나올 수 있어, 발표에서는 (라)를 성능으로, (마)는 고친 효과로만 쓴다. 새 메뉴로 재려면 이 40개에 없는 메뉴로 정답표를 다시 매겨야 한다.

## 4. 메뉴 80개로 늘리기 (2차, 2026-11-26, 채우는 중)

3절의 (마)는 고친 뒤 같은 메뉴로 다시 잰 값이라 새 메뉴에서의 성능을 말하지 못한다. 그래서 1차와 겹치지 않는 메뉴 40개(M41~M80)를 같은 비율로 더 골라 같은 방법으로 잰다. `03_human_answer_key.py`는 고치지 않고 `04_human_answer_key_80.py`가 1차와 2차를 합쳐 80개로 같은 표를 낸다. 2차 사람 시트가 덜 찼으면 1차 결과(03 출력)와 2차 채운 칸 수만 내고 멈춘다.

1. 메뉴 고르기: 운영 서버에 사람들이 직접 적은 입력 중 1차에 없고 시험 계정이 아닌 것 10개(알밥, 국수, 돼지고기, 제육보와 가게나 브랜드 이름 알촌, 남월, KFC, 요아정, 베스킨라빈스31, 학식), 외국 음식 13개, 소스와 육수에 재료가 숨은 한식 11개, 식단 판단 6개(할랄 양고기 커리, 비건 라멘, 채식 만두, 콩고기 불고기, 퀴노아 샐러드, 비건 크림 파스타). 기본 메뉴 이름과 같은 것(팟타이, 케밥, 콩국수)은 직접 적기로 시험되지 않아 뺐다
2. 사람 시트: 같은 세 사람이 `data/human2_a_aninnom.csv`, `data/human2_b_ruty041.csv`, `data/human2_c_goni1130.csv`를 1차와 같은 기준(3절 1~3)으로 채운다. 다수결로 못 정한 칸은 `data/human2_decided.csv`(`id,태그,값,이유`)에 적는다
3. AI 기준 정답: 1차와 같은 방법(평가자 둘과 판정자)으로 만든 `data/consensus2.csv`. 사람 정답이 아니다
4. 시스템 답(`data/system2_v1.csv`~`system2_v3.csv`, 모양은 1차와 같고 `soft_tags` 열을 더했다)
   - (가) 낱말 표: 지금 운영 서버(0045, 0055 뒤)의 확실(`sure_tags`)과 약함(`soft_tags`). 1차의 (가)는 그때 서버 값이라 낱말 표 판이 다르다. 앱처럼 약함도 약한 표시로 센다(2차에서 퀴노아 샐러드, 비건 크림 파스타 둘만 있다)
   - (마) 판 3: 운영 서버에 시험 계정(`zz_eval2_`)으로 모임을 만들어 40개를 직접 적기로 올려 받은 답. 라자냐는 첫 요청이 모델 쪽 503으로 실패했고 10분 뒤 다시 받았다. 받은 뒤 시험 모임 4개와 계정 4개를 지웠다. 새로 생긴 음식 30개와 기존 입력 10개의 추정 값은 1차처럼 서버에 남는다
   - (나) 판 1, (라) 판 2: 그 판의 프롬프트와 응답 모양, 모델 순서, 8초 제한을 git 기록(`7316a7c`, `dcf501c`의 `logic.ts`)에서 그대로 가져와 Gemini에 직접 물었다. 서버 저장 규칙은 0023(판 1: 9개 밖 태그 버림), 0044(판 2: 메뉴 아님이면 태그 없음, 이유 없는 태그 버림)를 따라 걸렀다. 40개 모두 답을 받았다(판 1은 3개, 판 2는 4개가 두 번째 모델 답). 1차의 판 1, 판 2는 그때 서버 값이고 2차는 지금 다시 물은 값이라, 모델이 그 사이 바뀌었으면 그때와 다를 수 있다. (다) 합침은 판 1 답과 지금 낱말 표의 합집합이다
5. 출력은 방식마다 80개, 1차, 2차 줄을 따로 낸다. 새 메뉴에서의 성능은 (마)의 2차 줄로 본다

모델 답은 물을 때마다 조금씩 달라서(3절) 모두 한 번 뽑은 값이다.

## 앱과의 관계

```text
공공 인허가·오픈스트리트맵 → 01 전처리 → 가게 CSV ── 대조 ── 서버 가게 추출본
                                                             ↑ 실제 앱은 서버를 조회
낱말 표 + AI 판 1·판 2 답 → 02 오프라인 비교 ← 기준 정답(AI 평가자 둘 + 판정자)
                                   └ 결과로 기본 메뉴와 낱말 표를 고침(0045)
```

가게 CSV와 평가 코드는 수업 제출용이다. 앱은 이 폴더를 호출하지 않으며, 여기서 만든 결과를 서버에 자동 반영하지 않는다. 기본 메뉴 태그 고침은 사람이 읽고 0045 마이그레이션으로 따로 넣었다.
