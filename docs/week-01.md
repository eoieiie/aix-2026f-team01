## 연락 규칙 / Contact rule — 어디로, 몇 시간 내 응답

- 기본 연락 수단은 Discord. GitHub의 PR·Issue 알림이 `#github` 방으로 들어오도록 연동할 예정.
- 응답 시간은 평일 12시간 이내, 긴급한 사항은 이슈에 따로 표기. Task의 마감 기간을 정해 공유하고 반드시 그 기간 안에 끝낸다.
- 카카오톡은 당일 마감 같은 긴급 건만 쓴다.
- 회의에서 난 결론은 해당 Issue나 PR 댓글에 옮겨 적는다.서로 다른 작업을 해도 같은 판단 근거를 보게 하려는 것.
- 도구를 늘리면 우리가 한 일의 기록이 흩어지므로, 소통수단을 최소화한다. 

> 근거: "결과보고서는 백지에서 쓰지 않는다. 매주 활동지를 엮어 완성한다."

## 회의 규칙 / Meeting rule — 요일·시간·불참 처리

- 만나는 회의는 안건이 있을 때만 한다. 안건이 있으면 최대한 수업 직후에.
- 나머지는 Discord와 Issue로 처리한다.
- 주차 담당은 그 주 회의 진행과 활동지 작성·커밋을 맡고, 순번대로 매주 넘어간다.
- 불참할 때는 미리 알리고 Discord에 글로 남긴다. 그 사이 올라온 Issue는 각자 읽고 숙지한다.

## 기여 규칙 / Contribution rule — 1인당 주 최소 작업량

- 역할이 정해지면 명확하게 분담하고 맡기되, 본인의 맡은 역할 뿐만 아니라 서로의 영역을 확실하게 인지하고 진행 방향과 속도를 일치시킨다.  
- 일의 단위는 Issue 1개. 각 Issue에는 무엇을 만들지와 끝났다고 인정할 조건이 적혀 있어야 한다.
- 1인 주 1개 이상 Issue 완료. 이 개수는 코딩을 시작하는 날부터 적용한다. 그 전(문제 발굴,명세 작성 기간)에도 조사나 인터뷰, 명세 작업은 Issue로 올리되 개수는 세지 않는다.
- 작업은 브랜치에서 하고 PR로 올린다. **main에 직접 올리지 않는다.**
- **완료 조건이 없는 PR은 리뷰하지 않는다.**(완료 조건에 대한 기준은 추후 정할 예정) 


리뷰는 순번 돌아가며 맡는다. 처음 리뷰는 내 다음 순번 사람이 한다. 그 사람이 자리에 없으면 다음 순번으로 넘어간다.(방관, 정체 등을 방지하기 위함). 승인 1개를 받으면 머지하고, 검토 중인 게 쌓여 있으면 새 작업을 시작하기 전에 리뷰부터 비운다. 

> 근거: Verification Tax — "코드 작성에서 아낀 시간은 감사와 검증에 다시 쓰인다." / Little's Law — 들어오는 양만 늘리면 밀린 일이 끝없이 쌓인다.

**개발 방식.** 명세와 설계는 SDD로 하고 목표 수준은 Spec-Anchored로 둔다. 할 일 관리는 칸반. 요구는 계속 바뀔 수 있고 바뀌면 명세를 고친다. 다만 이미 시작한 일의 완료 조건은 그 일이 끝날 때까지 바꾸지 않는다. 진행 중에 기준을 고치면 통과 여부를 우리가 정하게 되기 때문이다.

> 근거: SDD — "명세는 정적인 문서가 아니라 시스템을 실제로 규율하는 운영 계약이다." / Spec Maturity — "이 과목은 현실적인 수준인 Spec-Anchored를 목표로 한다."

**도구.** 할 일 관리는 GitHub Projects, 명세와 문서는 저장소의 `docs/`, 리뷰는 PR.

## 갈등 처리 / Conflict rule — 의견이 갈릴 때

1. 명세와 완료 조건으로 판단한다.
2. 완료 조건을 맞추려고 코드를 고치는 것은 허용한다. 명세부터 고쳐 코드를 통째로 다시 만드는 방식은 쓰지 않는다.
3. 명세는 언제든 고칠 수 있다. 이미 시작한 일의 완료 조건만 예외다.
4. 그래도 안 갈리면 서로 사랑해준다. 맛있는 걸 먹으러 간다. 
5. 왜 그렇게 정했는지를 `PROMPTS.md`에 남긴다.

> 근거: Spec Maturity — "Spec-Anchored: 코드를 진실의 원천으로 두되 명세를 기준으로 삼고 테스트로 강제한다."

## **팀 공용 언어 / Working language** — 회의 언어 / 기록 언어

- 회의,기록,커밋 메시지,Issue는 한국어.
- 코드,변수 이름,브랜치 이름은 영어.
- 커밋 메시지는 `docs: 1주차 활동지 작성` 형식으로. 앞에 종류, 뒤에 내용.(세부적인 틀은 추후 결정)

## AI 사용에 대한 팀 합의 / Team agreement on AI use

AI에 맡기는 것: 보일러플레이트, 반복적인 리팩터링, 테스트 뼈대, 문법 확인.
사람이 직접 하는 것: 문제 정의, 명세와 완료 조건 작성, 전체 구조 설계, 보안 관련 코드, PR 승인 판단.

- 중요한 판단과 그 이유는 `PROMPTS.md`에 기록한다.
- **이해하지 못한 코드는 PR에 올리지 않는다.** 리뷰하는 사람은 올린 사람에게 동작 원리를 물을 수 있고, 답하지 못하면 승인하지 않는다.
- 마찬가지로 지정된 리뷰어가 코드를 읽다가 도저히 작동 원리가 이해되지 않는 부분을 발견하면, 반드시 리뷰를 반려한다.
- 남의 코드를 가져다 쓰면 출처를 적는다.
- **실제 개인정보를 AI 도구의 컨텍스트로 넣지 않는다.** 개인정보를 다루는 기능은 시작 전에 교수님께 여쭙는다.

> 근거: 수업의 AI 사용 규칙 4개 항목. "14주 발표에서 동작 원리를 질문한다"는 공지를 발표 직전이 아니라 매 PR 리뷰 단계에 미리 걸어두었다.
