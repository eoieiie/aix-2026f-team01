## 4장. 정의 — 기존 도구는 누가 안 찍었는지 기다린다
- 주장: 기존 투표·룰렛을 써 본 61명 중 77.0%가 불편했고, 가장 많은 이유는 "안 찍은 사람을 마냥 기다림"입니다
- 숫자: 기다림 54.1%, 후보에 못 먹는 음식 23.0%, 룰렛이 표를 반영 안 함 18.0%, 익명 아님 8.2%(61명 중, 복수 응답)
- 문제 문장: "모임은 메뉴를 정할 때 못 먹는 사람이 말하지 못하고, 안 찍은 사람을 기다리느라 5분 넘게 쓴다"
- 대본: 그래서 문제를 세 개로 좁혔습니다. 못 먹는 것은 말하지 않아도 알려야 하고, 다 고를 때까지 기다려 주되 끌지 않아야 하고, 마지막 결정은 사람이 아니라 표와 룰렛이 져야 합니다.

## 5장. 아이디어 — 앱이 고르지 않는다
- 주장: 추천 앱이 아니라, 투표와 룰렛이 고르고 앱은 지켜 주는 도구입니다
- 기존 서비스 비교 표(`docs/competitors.md`, 2026-11-16 확인): 카카오톡 투표, 오늘뭐픽, 우리뭐먹지, 오늘 뭐 먹지?(사다리), 점심 룰렛 대 밥BTI
  - 설치 없이 링크로 참여: 밥BTI만 됨
  - 못 먹는 것: 한 번 등록하면 모든 모임에 쓰이고, 누가 못 먹는지는 서버에도 남지 않음
  - 룰렛 조각 크기가 표 수에 비례
- 비슷한 점도 적는다: 룰렛, 결과 카드, 먹은 기록은 다른 앱에도 있음
- 대본: 비슷한 앱은 많습니다. 다만 대부분 앱이 메뉴를 골라 줍니다. 저희는 고르는 책임을 모임의 투표와 룰렛에 남기고, 앱은 못 먹는 사람이 밀려나지 않게 지키는 데 집중했습니다.

## 9장. 전처리 — 651곳에서 182곳으로
- 주장: 좌표를 바꾸고, 정문 1.2km 안 식사 가게만 남겼습니다
- 단계(`docs/dataset.md` 3~5절)
  1. 좌표 변환: EPSG:5174(Bessel 중부원점 TM) → WGS84(위도·경도). 오픈스트리트맵에도 있는 밀플랜비, 도스마스로 대조해 2m 안
  2. 범위: 정문(37.2998, 126.8369)에서 1.2km, 하버사인 거리
  3. 업태 거르기: 카페 등 "기타", 술집, 닭이 없는 호프 제외
  4. 겹침 제거: 오픈스트리트맵에 이미 있는 가게 제외
  5. 대표 메뉴 짐작: 가게 이름과 업태(중국식 → 짜장면, 짬뽕, 탕수육)
- 전처리 전·후 한 줄: `[원본 CSV 한 줄과 서버 한 줄, 혁준 dataset.md에서 옮김]`
- 대본: 처음에는 기준점을 잘못 잡아 370m 어긋났는데, 팀원 리뷰에서 잡혀 다시 골랐습니다. 이 이야기는 AI 장에서 다시 말씀드리겠습니다.

## 10장. 코드 — 직접 적은 메뉴가 "못 먹는 사람이 있어요"가 되기까지
- 주장: 생성형 AI는 직접 적은 메뉴의 숨은 재료를 짚는 데만 씁니다
- 과정(파일과 함수, 10~20줄 발췌 위치)
  1. 직접 적기: `src/api/sessions.ts` `addCustomCandidate` → 서버 `add_custom_candidate`가 낱말 표(`food_keywords`, 0008) 태그를 먼저 붙여 후보를 바로 올림. 이어서 `functions.invoke('guess-ingredients', { food_id })`를 기다리지 않고 부름(sessions.ts 291줄 근처)
  2. 서버 확인: Edge Function `supabase/functions/guess-ingredients/index.ts`가 부른 사람 JWT로 `ai_ingredient_request`(0023) 호출 → 직접 적은 메뉴인지, 판 참여자인지, 저장한 답이 있는지, 하루 상한(200)을 서버가 판단
  3. AI 호출: `logic.ts`의 `buildRequestBody`(메뉴 이름 한 줄만 보냄), `RESPONSE_SCHEMA`(재료 9개 enum만 고를 수 있는 JSON), `SYSTEM_PROMPT`(흔한 버전 3~4개를 떠올려 재료를 모두 합치고, 애매하면 넣는다). 8초 안에 답이 없으면 다른 작은 모델로 한 번 더
  4. 걸러서 저장: `parseGuess`가 9개 밖 값을 버림 → `ai_ingredient_apply`(0023 50~85줄)가 `tags`에 합집합으로 더하기만 하고 `refresh_vetoes`로 그 판을 다시 판정
  5. 화면: 실시간 구독으로 후보 카드에 "AI가 추정한 재료 · 해산물, …"와 "못 먹는 사람이 있어요"(`src/components/candidate-card.tsx`). 누르면 재료마다 이유 한 줄
- 발췌 추천: `logic.ts` `RESPONSE_SCHEMA`와 `parseGuess`(합쳐 약 20줄), 0023 `ai_ingredient_apply`의 합집합 줄
- 그림: 분짜 후보 카드 펼친 화면(새로 찍을 화면: "분짜" 직접 적기, 해산물 못 먹는 친구)

## 예상 질문과 답

1. **생성형 AI가 주제인데 AI를 너무 적게 쓴 것 아닌가요?**
   일부러 좁혔습니다. 메뉴를 AI가 고르면 "모임이 정했다"는 가치가 사라지고, 추천 앱은 이미 많습니다(5장 비교). 대신 낱말 표가 못 잡는 숨은 재료를 짚는 자리에 썼고, 재료 9개만 고르게 하고 더하기만 하게 해서 AI가 틀려도 못 먹는 사람이 손해 보지 않게 했습니다.
2. **AI가 재료를 틀리면 어떻게 되나요?**
   애매하면 "들어 있다"로 봐서 괜히 붙는 쪽으로 틀립니다. 그 경우 후보가 지워지지 않고 알림만 붙어서 투표는 그대로 할 수 있습니다. 얼마나 틀리는지는 정답표 실험으로 잽니다 `[11/26 이후 숫자]`.
3. **못 먹는 사람이 누구인지 정말 안 드러나나요?**
   서버에는 "이 후보가 걸렸다"만 남고 원인은 저장하지 않습니다. 다른 사람의 표도 서버 권한으로 막혀 API로 조회해도 0행입니다(AC, pgTAP). 모임 카드 집계는 3명 이상일 때만 보입니다.
4. **식당 정보는 정확한가요? 지도 앱과 뭐가 다른가요?**
   위치와 업태는 행정안전부 인허가 자료라 정확하고, 메뉴는 업태로 짐작한 값이라 "OO 있어요"는 메뉴가 맞을 때만 보입니다. 지도 앱처럼 찾는 것이 아니라, 메뉴가 정해진 뒤 그 메뉴를 파는 학교 앞 가게만 보여 줍니다. 가게를 누르면 카카오맵으로 넘어갑니다.
5. **수업 인원이 한꺼번에 들어오면 버티나요? 파이썬이 아닌데 소스는 어떻게 내나요?**
   실제 서버에 가상 사용자 80명으로 시험해 서버 함수 실패가 없었습니다(13장). 소스는 TypeScript 앱 저장소 전체를 실행 방법 README와 함께 한 폴더로 냅니다(`scripts/make-submission.sh`, PR #104). `[11/25 교수님 답 반영]`
